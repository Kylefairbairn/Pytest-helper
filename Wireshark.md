# Wireshark test capture tool

A small dependency-free Python wrapper around the `tshark` executable already
installed on the test-controller VM. Python does not need PyShark or native
packet bindings.

## Can the controller VM see everyone's traffic?

Not automatically. A NIC normally sees broadcasts/multicasts delivered to its
segment and unicast addressed to itself. To capture VM and development-board
unicast traffic, make the controller a deliberate observation point:

1. **Best general setup:** configure a physical-switch SPAN/mirror session with
   the board-facing ports/VLAN as sources and a controller capture NIC as the
   destination.
2. **Virtual traffic:** enable port mirroring on the hypervisor bridge/vSwitch,
   or attach the capture VM to a mirrored port group.
3. **Inline option:** route or bridge the test network through the controller.
   This guarantees visibility but makes the controller part of the data path.

Use a dedicated capture NIC with no IP address when practical. It avoids test
traffic generated by the controller and reduces accidental exposure.

## Install

```bash
python -m pip install -e .
tshark -D
```

Grant packet-capture permission to `dumpcap`/the service account using your OS
package's supported method. Do not run the whole pytest process as root.

## Python interface

```python
from pathlib import Path
from traffic_capture import CaptureConfig, CaptureProfile, TsharkCapture

capture = TsharkCapture(CaptureConfig(
    interface="ens224",
    profile=CaptureProfile.MULTICAST_RTP,
    rtp_port_range=(5004, 5999),  # omit when the product uses dynamic/unknown ports
))

capture.start()
# exercise the system under test
result = capture.stop()
saved = capture.save_pcap(Path("artifacts/pcaps/REQ-1234.pcapng"))
```

`stop()` sends SIGINT so tshark closes the file cleanly. `save_pcap()` copies
atomically, so reports never observe a half-written artifact.

For an arbitrary BPF expression, set `capture_filter`, for example:

```python
CaptureConfig(interface="ens224", capture_filter="host 10.20.0.15 and udp")
```

Capture filters are used instead of Wireshark display filters because unwanted
packets are discarded before they reach disk. RTP itself has no universal port,
so the safe default for the `multicast_rtp` profile is multicast UDP. A known
RTP port range makes it much tighter.

# Capturing and Verifying RTP Traffic

```python
from pathlib import Path

from traffic_capture import (
    CaptureConfig,
    CaptureProfile,
    TsharkCapture,
)


def test_multicast_rtp():
    capture = TsharkCapture(
        CaptureConfig(
            interface="ens224",
            profile=CaptureProfile.MULTICAST_RTP,
            rtp_port_range=(5004, 5999),
        )
    )

    # Start capturing packets.
    capture.start()

    try:
        # Run the action that should generate RTP traffic here.
        # Example:
        # product.start_rtp_stream()
        pass
    finally:
        # Always stop tshark cleanly.
        capture.stop()

    # Save the completed capture.
    pcap_path = capture.save_pcap(
        Path("artifacts/pcaps/REQ-1234.pcapng")
    )

    # Force UDP port 5004 to be decoded as RTP and verify RTP was found.
    result = capture.verify_rtp(
        udp_port=5004,
        display_filter="ip.dst == 239.1.1.1",
    )

    assert result.is_rtp, f"No RTP packets found in {pcap_path}"
    assert result.packet_count > 0

    # Optional packet-level checks.
    first_packet = result.packets[0]

    assert first_packet.destination_ip == "239.1.1.1"
    assert first_packet.destination_port == 5004

    print(f"Saved capture: {pcap_path}")
    print(f"RTP packets found: {result.packet_count}")
    print(f"SSRC: {first_packet.ssrc}")
    print(f"Payload type: {first_packet.payload_type}")
```

Run the test from the project directory:

```bash
python3 -m pip install -e .
pytest -v tests/test_multicast_rtp.py
```

Replace:

- `ens224` with the controller VM’s capture interface.
- `5004` with the actual RTP UDP port.
- `239.1.1.1` with the expected multicast destination.
- The `pass` statement with the action that starts the RTP stream.
```
## pytest integration

Register the included plugin in the test suite's `conftest.py`:

```python
pytest_plugins = ["traffic_capture.pytest_plugin"]
```

Then request the fixture:

```python
def test_stream_starts(traffic_capture):
    # capture is already running; exercise the requirement
    ...
```

```bash
pytest --capture-interface ens224 --capture-profile multicast_rtp
```

The fixture makes one pcapng per pytest requirement. Product or capability
selection only changes which requirement tests run; it does not change capture
ownership.

## Keeping captures tight

- Use a switch/vSwitch mirror scoped to the test VLAN, then a BPF capture filter.
- Prefer a known host/subnet and known RTP port range over protocol heuristics.
- Keep full packets by default. A `snaplen` can reduce payload size, but truncated
  RTP is less useful when debugging corruption or sequence problems.
- Start immediately before the stimulus and stop immediately after the assertion.
- Keep `-n` enabled to prevent DNS/name-resolution traffic and delays.
- For long soak tests, add tshark ring-buffer options such as `-b filesize:102400
  -b files:4`; the current API intentionally avoids silent data loss by default.

## Useful next capabilities

- Store capture metadata beside the pcap: requirement ID, product, capability,
  interface, BPF filter, software version, and start/stop timestamps.
- Add post-capture assertions using `tshark -r file -Y ... -T fields`, keeping
  capture and analysis separate and preserving the original evidence.
- Add profiles from YAML configuration rather than embedding product-specific
  filters in tests.
- Attach only failed-test pcaps to pytest-html, while retaining all pcaps in the
  build artifact directory.
- Add a remote capture adapter later (`ssh controller tshark ...`) without
  changing the fixture or test API.
